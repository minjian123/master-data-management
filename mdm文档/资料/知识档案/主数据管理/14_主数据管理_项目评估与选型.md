## 1. 定位 <a id="position"></a>

本篇把前 12 篇的通用结论落到 **BMS 平台与 mdm 产品**的具体场景，做**评估与选型映射**，供规划讨论与设计引用。**默认口径以规划与设计为准**，本篇为评估参考。

> **范围口径（2026-10-07 确认）**：mdm 统一管理的是**跨业务共享的主数据**（组织 / 供应商 / 客户 / 物料等）；用户 / 角色 / 菜单 / 权限 / 字典 / 系统参数等**平台运行必需的基础数据仍归 BMS 平台**。即「MDM 统一管理主数据」，而非「接管平台基础数据」。

## 2. 本项目的主数据定位 <a id="classification"></a>

| 数据 | 归属 | 依据 |
| --- | --- | --- |
| 部门 / 岗位 / 用户-岗位关联 / 角色-岗位、角色-部门分配 | **mdm 组织域** | 跨域共享、需统一口径 |
| 供应商 / 客户 / 物料等 | **mdm 各主数据域** | 被采购 / 销售 / 仓储等共同引用 |
| 用户 / 角色 / 菜单 / 权限 / 字典 / 系统参数 | **BMS 平台** | 平台运行必需基础数据，非跨业务共享主数据 |
| 仓库 / 库位 | biz 仓储业务 | 与库存交易一体，非纯主数据 |
| 交易数据 / 单据 / 流转状态 | 各业务产品 | 业务流转，非主数据 |

> 判定采用《[02 概念与边界](02_主数据管理_概念与边界.md)》的判定尺；域划分与标识符登记见《[mdm 主数据管理规划](../../../规划/mdm主数据管理规划.md)》。

## 3. 实现风格选型：集中式（Centralized） <a id="style"></a>

| 判据（见《[04 四种实现风格](04_主数据管理_四种实现风格.md)》） | 本项目情况 |
| --- | --- |
| 源系统能否由枢纽唯一接管？ | **能**——本项目从零构建，无「多套历史主数据库各自为政」包袱 |
| 需要回写源系统吗？ | 不需要——业务产品不自建主数据，只引用 |
| 结论 | **集中式**：mdm 是主数据唯一创建方与权威出口 |

**为什么不选注册 / 合并 / 共存**：本项目不存在「多个源系统各存一份权威主数据」的历史包袱，注册与合并的「只读索引 / 汇总」价值不成立；共存的「双向回写」复杂度无必要。集中式最简、最一致。

## 4. 架构与分发选型 <a id="architecture"></a>

| 维度 | 本项目选择 | 依据篇目 |
| --- | --- | --- |
| 部署架构 | 逻辑集中、物理分布（按域拆服务） | 《[05 架构模式与枢纽拓扑](05_主数据管理_架构模式与枢纽拓扑.md)》 |
| 拓扑 | Hub-and-Spoke（mdm 为 hub） | 同上 |

| 分发 | 契约读 + 事件订阅 | 同上 |

| 一致性 | 最终一致 + Outbox + 幂等（+ 屏障按需） | bms《微服务演进规划》《架构设计 · 服务间通信与一致性》 |

## 5. 数据标准与质量口径 <a id="standard-quality"></a>

- **编码**：主键用雪花 ID（稳定、无业务含义），另设**业务码 / code** 承担对外可读标识与逻辑外键（见《[06 数据标准与数据模型](06_主数据管理_数据标准与数据模型.md)》）；
- **属性**：围绕跨业务共享特征建模，业务专属属性留业务侧；域内关系（如岗位归属部门）随域管理，跨域关系用逻辑外键；
- **质量**：集中式下**前移**到「录入校验 + 唯一约束」，靠标准从源头控质；存量导入才做一次性清洗（见《[08 数据质量与匹配合并](08_主数据管理_数据质量与匹配合并.md)》「与本项目的对照」节）。

## 6. 治理与组织口径 <a id="governance"></a>

- **负责人制**：每个主数据域明确**数据负责人（owner）**与**数据管家（steward）**（按域授权、审批流角色）；
- **系统承载**：审批走平台工作流、责任靠审计哈希链、质量靠校验规则库、分发靠事件与台账（复用 BMS 平台能力，不重复实现）；
- **与平台边界**：治理的「组织与制度」是产品侧长期事项，「技术承载」复用平台（见《[07 数据治理与组织](07_主数据管理_数据治理与组织.md)》）。

## 7. 构建方式：自建（而非采购） <a id="build"></a>

| 判据（见《[12 开源与商业产品盘点](12_主数据管理_开源与商业产品盘点.md)》） | 本项目情况 |
| --- | --- |
| 是否与业务深度绑定、通用产品难适配？ | 是（与 BMS 平台 / biz 业务深度耦合） |
| 是否已有成熟平台基座只需补域？ | 是（认证 / 权限 / 事件 / 审计 / 工作流 / 文件等已具备） |
| 是否有自主可控要求？ | 倾向自主可控、避免异构套件 |
| 结论 | **自建**：mdm 作为产品仓库独立演进，复用平台能力 |

## 8. 组织服务（bms org 服务）归位 <a id="org-service"></a>

现状核查（2026-10-07）：bms 存在 `backend/services/org` 服务，且用户 / 账号、角色已先后迁出至 platform，**其现存职责仅剩组织主数据占位路由**（`/org/users`、`/org/posts`、`/org/dept-tree`、`/org/resolve-names`），与 **mdm 组织域高度重叠**。

| 问题 | 结论方向 |
| --- | --- |
| bms org 服务与 mdm 组织域重复 | **退役 bms org 服务**，组织主数据所有权归 **mdm 组织域** |
| 组织主数据只读出口（数据源 / 名称回显） | 由 **mdm 组织域实现**（规划与架构总纲已声明迁入 mdm） |
| 用户-部门 / 用户-岗位关系 | 归 **mdm**（`org_user_dept` / `org_user_post`，各带主要项标记）；经 **mdm 契约 / 事件**；`sys_user` 不落组织字段（原 `dept_id` 逻辑外键设计 2026-10-09 取消） |
| 用户删除等联动 | 经事件驱动 mdm 清理（如 `sys.user.deleted`） |

> 具体退役步骤、契约迁移、标识符与服务目录对齐、影响面清单属**规划讨论**事项，不在本篇展开；本篇只给「方向与依据」。讨论结论回写《[mdm 主数据管理规划](../../../规划/mdm主数据管理规划.md)》。
