## 1. 概述 <a id="overview"></a>

**数据标准是主数据管理的核心内容**——没有标准，后面所有工作都是无用功。标准通过「统一定义 + 统一规则」实现跨组织、跨部门、跨系统、跨流程的数据集成与共享。本篇讲标准的构成、编码规则与模型设计。

## 2. 数据标准的三分类 <a id="three-kinds"></a>

| 类别 | 明确什么 | 举例 |
| --- | --- | --- |
| **数据标准** | 主数据的编码规则、分类标准、命名规范、编码颗粒度、属性规范、模型标准 | 物料模型与属性描述规则 |
| **管理标准** | 组织、制度、流程、职责、申请与变更规范 | 「谁申请、谁审核、谁创建」的流程与责任 |
| **服务标准** | 集成服务接口规范、开发规范、外围系统接入规范 | 主数据分发接口契约与接入规范 |

> 标准体系要**适合本企业业务、适应发展**，不能「先入为主」也不能「直接照搬」；同一主数据名称只出现一次，术语前后一致。

## 3. 编码规则七原则 <a id="code-rules"></a>

编码是主数据标准的核心。一套好的编码体系遵循七项原则：

| 原则 | 含义 |
| --- | --- |
| **唯一性** | 一个实体只有一个编码 |
| **稳定性** | 编码规则一旦确定，不轻易变动 |
| **简易性** | 码位尽量短，便于操作与识记 |
| **规范性** | 编码类型、规则、结构统一 |
| **统一性** | 同一主数据在全企业范围内编码唯一，不各自为政 |
| **可扩展性** | 预留扩展空间，新增类别不乱体系 |
| **可理解性** | 尽量沿用业务习惯与既有标准 |

常见编码结构：

| 结构 | 说明 | 取舍 |
| --- | --- | --- |
| 纯流水码 | 无业务含义（序列 / 雪花 ID） | 稳定、简单，但不可读 |
| 分类码 + 顺序码 | 码内含分类层次，便于归类检索 | 最常用；分类层次不宜过细，分类变动会牵动编码 |
| 业务码 | 有语义的短码 | 可读易用，但易冲突、需避让 |

> 本项目主键用雪花 ID（稳定、无业务含义），与其配套的是**独立的业务码 / code 字段**承担对外可读标识与逻辑外键引用——主键与业务码分离，是兼顾稳定与可读的常见做法。

## 4. 属性规范与数据模型 <a id="model"></a>

主数据建模的核心是确定**这类主数据需要哪些属性**。原则：

- **围绕跨部门、跨业务、跨系统的共享特征确定属性**，不把每个部门的需求全部堆进来；
- 识别**真正跨业务共享**的属性，业务专属属性留在各自业务侧；
- 区分**核心属性**（共享、必填）与**扩展属性**（按业务可选）。

主数据模型通常分三层：

```mermaid

    B["业务模型<br/>业务视角的实体与关系"] --> L["逻辑模型<br/>实体 / 属性 / 关系 / 约束（跨库通用）"]
    L --> P["物理模型<br/>字段类型 / 索引 / 方言落点"]

    class B,L,P k
```

| 层 | 内容 | 归属文档 |
| --- | --- | --- |
| 业务模型 | 实体清单、业务实体关系 | 概要设计 |
| 逻辑模型 | 属性、类型、约束、关系（与方言无关） | 数据规范 |
| 物理模型 | 字段级结构、索引、方言差异 | 数据表文件 / 方言特性 |

> 本项目口径：**表结构只认表文件**，字段级结构不复制到需求 / 任务 / 设计正文；通用约定（公共字段、类型映射、时间、多语言附表等）只在《数据规范》维护，表文件不重复（见 bms《数据库开发规范》与本项目《数据库设计》）。

## 5. 分类、字典与层次 <a id="taxonomy-dict"></a>

标准里除了编码与属性，还有三个常被忽视的构件：

- **分类体系**：归集与检索维度（品类树、组织树），设计要点见《[03 数据域划分与分类](03_主数据管理_数据域划分与分类.md)》；
- **数据字典 / 参考数据**：受控值集（状态、类型、单位），应集中管理、随需求快速增补；
- **层次结构**：实体间层级关系（组织树、科目树），常需支持移动、级联维护。

## 6. 标准的落地与维护 <a id="maintain"></a>

- **标准先立后建**：先定标准，再建平台、再清存量；
- **标准变更受控**：数据标准的变更须走治理流程，回写文档与规范；
- **标准与实现分离**：标准定义「应该是什么」，实现（表结构、接口）随标准传导，避免两处口径。
