## 1. 概述 <a id="overview"></a>

主数据管理的第一个问题不是「怎么管」，而是「**什么算主数据**」。企业数据种类繁多，误把交易数据、参考数据当主数据来管，会做无用功；漏掉真正需要共享的实体，又会让下游继续各建一套。本篇先划清边界。

## 2. 企业数据的六种类型 <a id="six-types"></a>

IBM 把企业数据分为六类，主数据只是其中一类：

| 类型 | 含义 | 示例 | 是否归 MDM |
| --- | --- | --- | --- |
| **主数据** | 描述关键业务实体的核心数据 | 客户、产品、供应商、组织、员工、位置 | **是** |
| 交易数据 | 业务事件与流水 | 销售订单、发票、付款单、出入库单 | 否（归业务系统） |
| 参考数据 | 用于分类其他数据的代码表 | 国家/地区、币种、计量单位、行业分类 | 归 RDM（参考数据管理与 MDM 常合并治理） |
| 元数据 | 「关于数据的数据」 | 表结构、报表定义、数据血缘、日志 | 否（归元数据管理） |
| 层次数据 | 数据之间的关系结构 | 组织架构、产品线、科目树 | 常作为主数据的层次结构（归 MDM 一并管） |
| 非结构化数据 | 文档、邮件、图片、音视频 | 合同扫描件、产品图、PDF 规格 | 否（归内容/文件管理） |

> 参考数据（Reference Data）与主数据（Master Data）最容易混淆：**参考数据是「给主数据和交易数据分类用的受控值集」（如币种、国家码），主数据是「被引用的业务实体本身」（如某个具体客户）**。二者常一并治理，但管理目标不同：RDM 管代码值的统一，MDM 管实体的唯一与可信。

## 3. 主数据的判定特征 <a id="traits"></a>

一个实体是否值得作为主数据管理，看五个特征：

| 特征 | 含义 |
| --- | --- |
| **跨域共享** | 被两个及以上业务部门 / 系统共同引用（最核心的判据） |
| **稳定** | 变动频率低、生命周期长，相对交易数据「波动小」 |
| **权威** | 需要有一个被各方认可的唯一来源（Source of Record） |
| **高价值** | 影响决策、运营、合规，错误代价大 |
| **复杂** | 属性多、关系多（层次、关联），跨系统口径易分歧 |

判定尺（行业通行）：

- **「被多产品 / 多域共同引用、需统一口径」→ 归 MDM**；
- **「只被单一业务使用、且随该业务交易流转」→ 归业务系统**；
- **「用于分类受控、值集有限且相对稳定」→ 归参考数据管理**。

## 4. 与相邻概念的区别 <a id="neighbors"></a>

| 概念 | 关注点 | 与 MDM 的关系 |
| --- | --- | --- |
| **MDM** | 核心业务实体的唯一可信版本 | 本体 |
| **PIM**（产品信息管理） | 面向销售渠道的产品内容（描述、图片、营销文案） | PIM 是产品主数据的**内容侧延伸**；MDM 管产品档案本体，PIM 管渠道发布内容 |
| **RDM**（参考数据管理） | 受控代码值集的统一 | 与 MDM 常合设，职能互补 |
| **CDP**（客户数据平台） | 客户行为与画像、营销触达 | 用客户主数据做支撑，但不管理主数据权威源 |
| **数据仓库 / 数据湖 / 数据中台** | 面向分析、汇聚历史与明细 | 数仓「存历史、面向分析」；MDM「只存当前最新权威版本、面向运营共享」，二者数据流向与目标不同 |

> 关键区分：**数仓的 ETL 以批量为主、保留历史；MDM 初始加载用 ETL，运行时以实时整合为主，且只关注当前最新主数据**（主数据不带交易流水历史）。

## 5. 常见主数据域 <a id="domains"></a>

业界常见主数据域（不同行业取舍不同）：

| 类别 | 典型域 |
| --- | --- |
| 客户与伙伴 | 客户、潜在客户、渠道、联系人 |
| 产品与物料 | 产品、物料、SKU、品类、BOM |
| 供应链 | 供应商、承运商、仓库/库位 |
| 组织与人员 | 组织架构、部门、岗位、员工、成本中心 |
| 财务 | 会计科目、银行账户、税种税率、结算方式 |
| 通用参考 | 计量单位、币种汇率、国家地区、行业分类 |

> 本项目已定与预留的主数据域见《[03 数据域划分与分类](03_主数据管理_数据域划分与分类.md)》与《[mdm 主数据管理规划](../../../规划/mdm主数据管理规划.md)》「主数据域全景」节。

## 6. 边界划错的代价 <a id="cost"></a>

| 错误 | 后果 |
| --- | --- |
| 把交易数据纳入主数据 | 主数据枢纽被高频单据淹没，失去「稳定共享」定位 |
| 把该共享的实体留在业务系统 | 各系统继续各建一套，编码各异，MDM 形同虚设 |
| 主数据与数仓职责混同 | 历史与当前口径打架，审计与对账困难 |
| 参考数据与主数据混管 | 更新频率与治理流程错配（代码表要快速增补，实体要走审批） |
