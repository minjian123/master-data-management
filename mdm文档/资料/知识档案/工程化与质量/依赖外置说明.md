## 1. 目的与适用 <a id="purpose"></a>

mdm 的前端 `node_modules` 与后端 `.venv` **都不落仓库树**，整体外置到本机**本地依赖仓**，项目原位只留指向依赖仓的符号链接。收益两条：

- **仓库树干净**：约 668M 依赖不进 git（`.gitignore` 已忽略），提交、备份、跨机同步都只带源码。
- **检索零污染**：glob / ripgrep / IDE 搜索默认**不跟随符号链接**，全局检索不会翻进依赖内容。

本机制与平台基座（bms）侧《pnpm 部署使用说明》《uv 部署使用说明》**同口径**，但 mdm 有若干产品侧差异（工作区根位置、跨仓基座包、跨拓扑软链），差异见第 5 节。

> 本文是**产品侧机制记录**：说清 mdm 怎么做、为什么这么做、与 bms 差在哪。基座侧的通用做法以 bms 知识档案为准，本文不复制。

## 2. 落点与目录形态 <a id="layout"></a>

```text
mdm/                                   # 产品仓库根（脚本在此执行）
├── scripts/tools/deps/                # 依赖外置脚本（外置 / 还原 / 重装 三入口）
│   ├── 外置依赖.sh                    # node_modules 与 backend/.venv → 依赖仓 + 原位符号链接
│   ├── 还原依赖.sh                    # 符号链接移除，依赖搬回项目原位（装依赖前必做）
│   └── 重装依赖.sh                    # 还原 → 安装（pnpm / uv）→ 再外置（闭环）
├── backend/
│   └── .venv -> <依赖仓>/backend-venv                                 # 符号链接（外置态）
├── frontend/                          # pnpm workspace 根（pnpm-workspace.yaml 所在）
│   ├── node_modules -> <依赖仓>/frontend/node_modules                 # 符号链接（外置态）
│   ├── modules/org/node_modules -> <依赖仓>/frontend/modules/org/node_modules
│   └── packages/api-types/node_modules -> <依赖仓>/frontend/packages/api-types/node_modules
└── deploy/.env                        # 可选：仅当需覆写依赖仓位置时创建（见第 3 节）

<依赖仓>/                              # 本地依赖仓（默认 $HOME/dev-deps/mdm，仓库外）
├── backend-venv/                      # 后端虚拟环境（uv 项目环境）
└── frontend/
    ├── node_modules/                  # 实际依赖内容（含 .pnpm 内容寻址树）
    ├── modules/org/node_modules/
    └── packages/api-types/node_modules/
```

每个 `node_modules` 与 `backend-venv` 都是**整体搬移**单位：目录连同其内部结构整树搬到依赖仓，原位替换为指向依赖仓的符号链接。日常开发常驻**外置态**。

## 3. 依赖仓位置与优先级 <a id="depsdir"></a>

脚本按以下顺序确定本地依赖仓（**环境变量 > 配置文件 > 缺省**）：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 `DEPS_DIR` | 临时切换用（如 `DEPS_DIR=/path/to/deps bash scripts/tools/deps/外置依赖.sh`） |
| 2 | `mdm/deploy/.env` 的 `DEPS_DIR=` | 需长期固定到非缺省位置时创建；该文件已 gitignore |
| 3 | 缺省 `$HOME/dev-deps/mdm` | **当前采用**：未创建 `deploy/.env`，走缺省 |

> 依赖仓路径属**本地资源信息**，不写入仓库文件；确需固定时写入已 gitignore 的 `deploy/.env`。
> mdm 与 bms **各用独立依赖仓**（bms 为 `$HOME/dev-deps/bms`），两侧脚本互不误伤。

## 4. 日常使用 <a id="usage"></a>

日常开发常驻外置态，直接跑门禁即可：

```bash
cd mdm/frontend && pnpm run check     # 前端 lint + typecheck + test
cd mdm/backend  && uv run pytest -q    # 后端用例（外置态下 uv 直接可用）
```

仅在**装依赖/改锁文件**时需要还原与重装（在 mdm 仓根）：

```bash
# 完整闭环：还原 → 安装 → 再外置
bash scripts/tools/deps/重装依赖.sh                  # 前后端一起（默认 --frozen 口径）
bash scripts/tools/deps/重装依赖.sh --frontend-only  # 只重装前端
bash scripts/tools/deps/重装依赖.sh --backend-only   # 只重装后端

# 分步入（等价于上面三步，按需单用）
bash scripts/tools/deps/还原依赖.sh          # 装依赖前必须还原（见下）
cd frontend && pnpm install --frozen-lockfile && cd ..
cd backend  && uv sync --frozen             && cd ..
bash scripts/tools/deps/外置依赖.sh

# 预览（不改动磁盘）
bash scripts/tools/deps/外置依赖.sh --dry-run
bash scripts/tools/deps/还原依赖.sh --dry-run
```

**为什么装依赖前必须先还原**：安装器面对符号链接形态的依赖目录行为不一致——pnpm 会误判依赖已齐而跳过，uv 可能要求 `--clear`。三步脚本入口已把「还原 → 安装 → 再外置」串好。

### 4.1 跨仓软链为什么要重写 <a id="crossrepo"></a>

mdm 前端把平台基座包（`@bms/core` / `@bms/ui-ep` / `@bms/api-types`）以 `file:` 引工作区 `bms` 克隆，并把 `../../bms/frontend/packages/*` 纳入本工作区成员（见任务 01_04 详细设计 §3.2）。这使 `node_modules` 内存在两类软链：

- **树内链**：目标在同一次搬移的 `node_modules` 之内（如 `.pnpm/...` 指向 `.pnpm/...`）。整树搬移后**相对关系不变**，天然继续有效。
- **跨拓扑链**：目标在项目内源码或兄弟仓 `bms`（如 `modules/org/node_modules/@bms/core -> ../../../../../../bms/frontend/packages/core`）。目录一搬走，**解析基准改变、必然断裂**。

外置脚本因此在**搬移前**先解析出这类链的绝对目标、搬移**后**重写为绝对路径（首次实测 9 条）。判据是「软链目标是否落在任一待搬移的 `node_modules` 根之外」——树内链不动，跨拓扑链才重写，**幂等**（已绝对化的链在下次外置时被识别为不在项目内而不再处理）。

> 注：这类绝对路径指向**本机工作区**，只在外置态生效；还原态由 pnpm 重新生成的仍是相对链。CI 现装态（`pnpm install --frozen-lockfile`）不受影响。

### 4.2 后端 venv 外置为什么可行 <a id="venv"></a>

后端 `.venv` 外置依赖基座的**工程根定位不穿透符号链接**：`bms_core.core.paths.resolve_backend_root()` 用 `Path.absolute()` 而非 `Path.resolve()` 向上搜 `alembic.ini` / `config.toml`。外置态下包体虽在依赖仓，`__file__` 的字面路径仍在 `<仓库>/backend/.venv/...` 之下，向上即可命中仓库内工程根。

该能力随 `backend/pyproject.toml` 锁定的 `bms-core` 提交 SHA 提供（2026-10-14 起，bms 提交 `02ee5314`）。若沿用 `Path.resolve()`，包体被解析到依赖仓、向上搜不到工程根而抛 `ConfigError`——外置即失败。

> 该基座能力同时为 `BMS_BACKEND_ROOT` 环境变量提供了显式覆盖入口（容器、非常规布局用），取值无效时 fail-closed 报错，不静默回落。

## 5. 与 bms 基座的差异 <a id="diff"></a>

| 维度 | bms 基座 | mdm 产品 | 处理 |
| --- | --- | --- | --- |
| 工作区根 | 仓库根 `bms/`（根有 `pnpm-workspace.yaml`） | `mdm/frontend/`（仓根**没有**） | 脚本按「脚本位置上跳三级定位仓根 + 校验 `frontend/pnpm-workspace.yaml`」，不复用 bms 脚本定位口径 |
| 依赖仓 | `$HOME/dev-deps/bms` | `$HOME/dev-deps/mdm` | 各自独立，互不误伤 |
| 跨仓基座包 | 本仓内（editable / workspace） | `file:` 引兄弟仓 `bms` 与纳入其工作区成员 | 外置时重写跨拓扑软链为绝对路径（见 4.1） |
| 后端 venv | `backend/.venv` 符号链接 → 依赖仓 `backend-venv` | 同口径（见 4.2） | 依赖基座 `02ee5314` 起的工程根定位 |

### 5.1 `.gitignore` 必须是 `node_modules`（无尾斜杠）<a id="gitignore"></a>

git 的忽略规则 `node_modules/`（**带尾斜杠**）只匹配**目录**，**不匹配符号链接**。外置态下 `node_modules` 是符号链接，若沿用带斜杠规则会被 git 当成未跟踪项、污染 `git status`。已在 `mdm/.gitignore` 改为无斜杠的 `node_modules`（与 bms 同口径），一处规则同时覆盖「真实目录」与「符号链接」两种形态。`.venv` 规则本就不带斜杠，无需调整。

### 5.2 后端 venv 外置的前置：`bms-core` 版本 <a id="venv-prereq"></a>

后端 venv 外置**依赖新版 `bms-core`**（含 `core/paths.py`）。mdm 经 `pyproject.toml` 的 `[tool.uv.sources]` 锁 bms 提交 SHA，故升级基座时要同步：

1. 确认目标 bms 提交已推送（CI 按 SHA 拉取，本地未推送的提交取不到）；
2. 改 `backend/pyproject.toml` 的 `rev`；
3. `cd backend && uv lock`（更新 `uv.lock`）→ `uv sync --frozen`；
4. 基座跨版本升级可能带入**平台契约变更**，如涉及在运服务公开契约，须重导快照：

   ```bash
   cd backend && uv run python -m ops.contract_snapshot export   # 重导 deploy/contracts/org.json
   uv run python -m ops.contract_snapshot check                  # 零漂移校验
   ```

## 6. 失败分支与排查 <a id="trouble"></a>

| 现象 | 成因 | 处置 |
| --- | --- | --- |
| `pnpm install` 报「依赖已齐」却不装 | 未还原，安装器见到符号链接误判 | 先 `还原依赖.sh`，或直接用 `重装依赖.sh` |
| `uv sync` 提示需 `--clear` | 未还原，`.venv` 仍是符号链接 | 同上 |
| 后端导入抛 `未找到后端工程根` | `bms-core` 早于 `02ee5314`（无 `paths.py`，仍用穿透软链的旧逻辑） | 升级 `rev` 并 `uv lock && uv sync --frozen`（见 5.2） |
| `Cannot find module '@bms/core'`（外置态） | 跨仓软链未重写为绝对路径 | 重跑 `外置依赖.sh`（幂等，会补写）；确认兄弟仓 `bms/` 在工作区同级 |
| 外置后 `git status` 冒出 `node_modules` | `.gitignore` 用了带尾斜杠规则 | 改为无斜杠 `node_modules`（见 5.1） |
| 契约快照零漂移检查不通过 | 基座升级带入平台契约变更 | 重导快照（见 5.2），确认属加性变更后随提交 |
| 脚本报「工作区定位失败」 | 在仓内叠加了仓名前缀（如 `mdm/scripts/...`），根被推深一层 | 在 mdm **仓根**按 `bash scripts/tools/deps/<脚本>.sh` 执行 |
| 符号链接指向 `<仓>/mdm/...` 幽灵目录 | 同上，路径前缀重复误建 | 删幽灵目录，按正确路径重跑 |
