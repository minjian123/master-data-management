## 1. 设计目标与范围 <a id="goal"></a>

承接需求 01-1：为 mdm 落**产品后端工程骨架与平台接入**，作为组织主数据域的承载基座。本设计收敛以下口径：

1. **代码级复用平台基座**：mdm 依赖 bms 共享基座库 **`bms-core`**（跨仓库 git 源依赖），服务应用经 `bms_core.application.BaseServiceApplicationFactory` 装配——与 bms 内部服务**同构**，不另起脚手架。
2. **独立服务接入**：mdm 按主数据域拆服务、每服务独立库（× 每租户），经 **OIDC + `/api/open` + 事件**与平台集成（《[平台可扩展性规划](../../../../../../../bms文档/规划/平台可扩展性规划.md)》「独立服务形态口径」节、bms《架构设计 · 模块注册》「独立接入边界」节）。
3. **服务目录本地登记 + 接入时写入平台**：mdm 侧以与 `bms_core` 同口径的注册要素（域简称 ↔ 表前缀 ↔ 业务码 ↔ 错误码段 ↔ 事件域）本地登记并自校验；接入时经平台注册通道写入 bms 服务目录（`sys_module` 升格，随平台 R4 提供）。
4. **首个服务 = 组织域（`org`）**：本任务只落**工程骨架与服务壳**（无业务表），组织主数据表与维护能力归 01_02、只读出口归 01_03。

**不在本期**：组织主数据域业务实现（01_02）；组织只读出口与契约（01_03）；前端接入（01_04）；完整治理（数据管家 / 审批流）。

### 1.1 现状与缺口 <a id="gap"></a>

- **现状**：mdm 仓库仅有文档，无任何后端 / 前端 / 部署 / CI 代码。
- **已有可复用（bms）**：共享基座库 `bms-core`（应用装配基座 / core 横切 / 数据访问底座 / 模块基类 / 能力域）、服务化地基（网关 / 服务目录 / 契约 / Outbox / 可观测 / 双类 JWT）。
- **缺口**：① mdm 侧无工程骨架与平台接入（本任务主体）；② ~~平台「产品服务接入」机制尚未交付~~ **已解除**（R4.1 / R4.2 / R4.3 后端侧全部就绪，见下）；③ ~~`bms-core` 的服务目录为平台固定清单，需支持产品服务记录注入~~ **已解除**（12_03 已交付）。

### 1.2 标识与登记路线（2026-10-07 拍板） <a id="identity"></a>

mdm 组织域**沿用《mdm 主数据管理规划》登记的 `org` 标识全套**（`service_key=org` / `module_key=org` / `table_prefix=org_` / `business_code=org` / `errcode_segment=33` / `event_domain=org` / 对外域段 `org`），**不回退、不改派**。为此顺序上**先由 bms 退役 `org` 服务释放标识、mdm 随后承接**（bms 需求域十一 任务 `11_01` 提前执行）：

- **为什么不能先起步、后改回**：注册要素一经登记即对外契约（架构 11「模块契约与产品下线」节），事后改派等于服务键 / 表前缀 / 事件域 / 错误码段 / 库名 / 表名 / 前端出口全量破坏性变更；
- **为什么能提前**：bms `org` 服务已空壳（无自有表、仅 4 个占位路由走 Null 实现），前端组织选择字段族**无业务页消费**（仅开发校验页与组件库测试引用）；
- **同批次协同改动**（bms 仓，见 [bms 11_01 详细设计](../../../../../../../bms文档/项目/02_后端基座与服务化地基/任务/11_组织服务退役/11_组织服务退役_01_组织服务工程退役/设计/01_详细设计_01_组织服务工程退役.md)）：① `org` 条目**易主**（平台能力 → mdm 产品，四要素不变）；② `PRODUCT_ROUTES` 增 `mdm/org → org`、产品档案 `mdm` 升 `enabled`；③ 网关「upstream 全量、服务级路由排除产品分组」；④ 基座库名前缀参数化（`[database].name_prefix`，mdm 配 `mdm`）；⑤ 产品服务合并「同 `module_key` 同值去重、异值即拒」。

> **登记架构（R，并发执行）**：bms 平台侧登记 `org` 行（供网关、迁移链、库键与表归属派生）+ mdm 侧 `service_records()` 注入**同值记录**并声明 `product_key="mdm"`（产品自持清单、产品维度自证）。两侧同值并存由基座合并去重保证一致，任一侧字段差异即拒启。

> **平台前置契约进度（2026-10-07）**：bms 需求域十二 **R4.1（12_01）/ R4.2（12_02）/ R4.3（12_03）后端侧均已交付**——产品档案 `sys_product` / `PRODUCT_CATALOG`、产品服务登记通道、产品公开契约产品侧自持、产品命名空间（`/api/{product_key}/v1/{domain}/...`，域段经 `PRODUCT_ROUTES` 显式映射）、开放接口 scope 登记、事件契约登记扩展点、**共享基座产品服务装配**（`service_records()` 注入 + `product_key` 声明 + 产品维度 fail-closed 校验 + 合并同值去重）。
>
> **余下平台侧待交付项**：仅 **R4.3 前端多包合并**（影响前端接入形态，归 mdm 需求 01-4，不阻塞本任务）。

- **分层职责与依赖方向**：`api → services → repositories → models / schemas` 单向；服务只依赖 `bms-core` 与自身包（《[后端开发规范](../../../../../../../bms文档/规范/后端开发规范.md)》「目录与分层职责」节）。

- **产品服务清单落点**：`backend/services/module_registry.py`（与 bms `bms_core/services/module_registry.py` 同口径，仅承载 mdm 自身产品服务行）。

## 4. `bms-core` 依赖与装配口径 <a id="assembly"></a>

### 4.1 依赖声明 <a id="dependency"></a>

```toml
# backend/services/org/pyproject.toml（节选）
dependencies = [
    "bms-core @ git+https://<内部 GitLab>/<组>/bms.git@<commit-sha>#subdirectory=backend/libs/bms_core",
    "fastapi>=0.115",
    "uvicorn[standard]>=0.30",
]
```

- **源与 ref**：`<内部 GitLab>/<组>/bms.git` 为**本地资源信息**，只写占位、不入公开文档，实际值以本地部署配置 / 凭据为准；`<commit-sha>` 取 **bms 已推送的提交 SHA**（本任务第一段产出，见 §1.2），构建可精确复现、并与「`org` 标识已释放」强绑定。
- **本地与 CI 同口径**：本地直接经内网访问 GitLab；CI 内以 `git config --global url."https://gitlab-ci-token:${CI_JOB_TOKEN}@<host>/".insteadOf "https://<host>/"` 注入凭据（`pyproject` 只写普通 https URL、**不含任何凭据**）。
- **升级**：bms 侧后续改动需同步升级 ref（人工，或后续接入 Renovate）。

### 4.2 应用装配 <a id="factory"></a>

```python
# backend/services/org/src/mdm_org/main.py（节选）
from bms_core.application import BaseServiceApplicationFactory
from bms_core.services.module_registry import ModuleRecord
from mdm_org.api.router import api_router
from services.module_registry import MDM_SERVICE_RECORDS

class ApplicationFactory(BaseServiceApplicationFactory):
    key: str = "application_factory"
    service_name: str = "org"
    service_title: str = "mdm 组织主数据服务"
    version: str = __version__
    contract_version: str = CONTRACT_VERSION
    product_key: str = "mdm"

    def service_records(self) -> tuple[ModuleRecord, ...]:
        return MDM_SERVICE_RECORDS

    def service_routers(self):
        return ConcurrentStableList([api_router])
```

- **强制走共享基座装配**：中间件链 / 异常处理 / 探针 / 引擎与租户源装配 / 插件装配一律由 `BaseServiceApplicationFactory` 承载，服务只声明身份与业务路由（《[后端开发规范](../../../../../../../bms文档/规范/后端开发规范.md)》「服务应用装配必须走共享基座（强制）」条）。
- **产品服务装配（bms 12_03，2026-10-07 交付）**：mdm 应用工厂**只额外声明两处**——① 覆写 `service_records()` 返回**本产品服务清单**（与 `bms_core` 同口径 `ModuleRecord`）；② 声明 `product_key = "mdm"`（**产品维度**）。基座据此形成**应用级服务目录视图**并做产品维度 fail-closed 校验（记录非空 / 均为产品分组 / 产品归属与声明一致 / 含运行服务登记行）。
- **两侧同值并存（2026-10-07 拍板，R 架构）**：bms 平台侧 `SERVICE_CATALOG` **也登记** `org` 行（`product` 分组 / `product_key="mdm"`，供网关、迁移链、库键与表归属派生），mdm 侧注入**同值记录**；基座合并按「**同 `module_key` 同值去重、异值即拒**」处理——任一字段差异（`status` / `contract_version` / `build_batch` 等）即拒启，两侧不漂移。

| 面 | 设计 | 依据 |
| --- | --- | --- |
| 认证与会话 | 复用平台 OIDC（Keycloak）：mdm 服务校验平台签发的**用户 JWT（`aud=api`）**与**服务 JWT（`aud=service`）**，JWKS 取平台 `/.well-known/jwks.json`；不实现登录 | bms《架构设计 · 认证与会话》《微服务演进规划》S4 |

| 服务间调用 | 出站经**服务 JWT** 调平台 / 其他服务公开契约；入站经 `require_service` 白名单；不跨库 | bms《架构设计 · 服务间通信与一致性》 |

| 事件总线 | 复用平台 RocketMQ 事件总线；mdm 注册事件域 `org.*`，发布 `org.dept.changed` / `org.post.changed` / `org.role_post.changed` / `org.role_dept.changed`；消费平台事件（如 `sys.user.deleted`） | bms《架构设计 · 事件总线》 |
| 服务目录 | **两侧同值（R 架构）**：bms 平台侧 `SERVICE_CATALOG` 登记 `org` 行（`product` 分组 / `product_key="mdm"`，供网关与派生面）+ mdm 侧 `service_records()` 注入同值记录（产品自持清单、产品维度自证）；基座合并**同值去重、异值即拒**。产品命名空间经 `PRODUCT_ROUTES` 映射登记（`mdm/org → org`） | bms《架构设计 · 模块注册》「独立接入边界」「服务目录与契约登记」节；bms 12_03 详设 §3 |
| 网关 | 复用平台 APISIX：对外仅经产品命名空间 `/api/mdm/v1/org/...`（服务级命名空间 `/api/org/v1` **不生成**——`render_routes()` 排除产品分组）；upstream `org:8000` 由 mdm Compose 服务名 `org` 解析 | bms《架构设计 · API 网关与边缘》；bms 12_02 详设 §5 |
| 复用的平台能力 | RBAC 权限码 / 审计 / 文件 / 字典 / 通知 / 检索 等一律经平台接口复用，不重复实现 | bms《架构设计 · 扩展点与插件化》「平台能力清单」节 |

## 6. 服务目录本地登记与配置 <a id="registry"></a>

### 6.1 本地服务目录 <a id="catalog"></a>

mdm 侧维护**产品服务清单**（与 `bms_core/services/module_registry.py` 的 `ModuleRecord` / 校验同口径），首条为组织域：

| 模块键 | 服务键 | 名称 | 表前缀 | 业务码 | 错误码段 | 事件域 | 分组 | 产品归属 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `org` | `org` | mdm 组织主数据服务 | `org_` | `org` | `33`（`33xxxx`） | `org`（`org.*`） | `product` | `mdm` |

- **唯一性校验**：启动 / CI 校验（模块键、表前缀、事件域、服务键、错误码段唯一且格式合法）；平台侧登记行（bms `SERVICE_CATALOG`）与本清单**同值**，由基座合并去重后参与校验（异值即拒）。
- **单一来源**：登记要素与《[mdm 英文简称规范](../../../../../../规范/英文简称规范.md)》及《[mdm 主数据管理规划](../../../../../../规划/mdm主数据管理规划.md)》「标识符登记」节一致；不一致以规划 / 规范为准。
- **产品维度**：本清单每条记录均为 `product` 分组且 `product_key="mdm"`；含运行服务登记行（`service_key="org"`）——产品维度 fail-closed 校验的四条断言（非空 / 产品分组 / 归属一致 / 含运行服务行）。

### 6.2 配置 <a id="config"></a>

- **最小差异配置**：`config.toml` 只写 mdm 特有项，其余走基座 `Settings` 默认值；`config.{dev,test,prod}.toml` 只覆盖环境差异（`docs_enabled` / `auto_create` / `sqlite_dir` / CORS 等）。**连接串 / 密钥一律经配置读取，不在代码 / CI 写死**（bms《AI开发规范》「配置唯一来源」红线）。
- **库名前缀**：`[database].name_prefix = "mdm"`（基座参数化项，默认 `bms`）→ 平台库 `mdm_org`、租户库 `mdm_org_{租户}`、归档库 `mdm_archive`；库键仍为基座相对键（`platform` / `tenant_{code}`），库名派生统一经基座 `database_name()`。
- mdm 特有配置（服务身份 / 网关接入 / 平台端点如 OIDC issuer、JWKS、RocketMQ / 库名前缀）**只经配置**，本地值不入库。

## 7. 部署与 CI <a id="deploy"></a>

- **部署**：`deploy/compose/` 提供组织域服务容器编排（**服务名 `org`**，与网关 upstream `org:8000` 对齐）+ 镜像（`deploy/Dockerfile`，按服务参数化、单服务）；连接平台基础设施（网关 / 认证 / Redis / RocketMQ / 库）**经配置与 `.env` 接入，不重复编排平台组件**（平台基础设施归 bms 部署）。每服务独立库（× 每租户），库名前缀 `mdm`（见 §6.2）。
- **CI**：`.gitlab-ci.yml`（`tags: [mdm]`）——**精简四 job**：`gate-smoke`（保留）、`backend-lint`（ruff check + format --check）、`backend-typecheck`（pyright strict）、`backend-test`（pytest + 覆盖率）、`backend-modules`（离线清单校验 + 契约快照零漂移）；**不建**镜像构建 / 三库集成 / 服务子流水线（骨架期无业务端点与表，随 01_02 / 01_03 引入）。CI 内拉取 bms 仓经 `CI_JOB_TOKEN` + git `insteadOf`（见 §4.1）。
- **迁移**：`alembic.ini` + `alembic/versions/` 按服务分链（目录 `org/`；本期**无脚本**，`ensure_development_schema` 跳过 → 不建业务表，与「本期无表」一致；`alembic.ini` 为基座定位工程根所必需）。运维脚本落 `backend/ops/`：离线清单校验（`check_modules`）、建库（`db_admin`）、按链迁移（`migrate`）。
- **公开契约**：产品侧自持——`backend/ops/contract_snapshot.py` 导出 `deploy/contracts/org.json` 并支持零漂移检查（骨架期仅探针 / 根路由与内部 `/api/v1` 结构）；**契约基线与破坏性变更门禁（oasdiff）待 01_02 / 01_03 有业务端点后引入**。

## 8. 失败分支与边界 <a id="edge"></a>

| 场景 | 处置 |
| --- | --- |
| 平台端点不可达（OIDC / JWKS / 事件） | 启动期配置校验失败即拒绝启动（fail-closed）；运行期按子能力降级策略（如 JWKS 缓存过期以旧公钥短暂容错后拒绝） |
| bms `org` 服务尚未退役 / 标识未释放 | **本任务前置**（bms 11_01 先执行并推送）：未释放时 `org` 在 bms 清单中为平台能力服务，mdm 注入同值记录会与平台行冲突（分组 / 产品归属不一致）→ 拒启；由「bms 先退役 + 推送 + mdm 锁该 ref」保证次序 |
| 两侧登记记录不同值 | 合并去重仅对**同值**生效；任一字段差异（分组 / `product_key` / `status` / `contract_version` / `build_batch` / `errcode_segment`）即判冲突拒启（fail-closed，不静默取一侧） |
| `bms-core` ref 不可达 / 不含所需能力 | 构建失败（不静默降级）——ref 锁 bms 提交 SHA（§4.1），构建可精确复现 |
| 服务目录与平台不一致 | 本地（离线 + 产品维度）校验拒绝启动；接库对账不可达时按基座口径告警放行并置 `catalog_degraded`（非目录权威服务） |
| 每服务独立库缺失 | 启动期建库 / 迁移校验失败即拒绝（与 bms 服务同口径）；SQLite 开发库按链表集自动建表（本期无脚本 → 不建业务表） |
| 库名前缀未配置 | 基座默认 `bms`（mdm 侧必须显式配 `mdm`，否则库名落到 `bms_org`）→ 以 `[database].name_prefix` 配置项 + 用例断言把住 |
