## 1. 设计目标与范围 <a id="goal"></a>

用户在部门管理复核时提出「部门需要代码」——核查确认：**部门（`org_dept`）只有名称、无任何编码**，而**岗位（`org_post`）已有岗位码**（`code`，唯一 + 格式约束 + 原「创建后不可改」）。本任务给部门补齐**部门编码**，并把岗位码与部门编码的口径统一。

1. **部门编码**：`org_dept` 增 `code`——必填、租户内唯一、格式受系统参数约束、**创建后可改**。
2. **存量回填**：迁移回填（`DEPT` + 定长 4 位序号）后置列非空并加唯一约束。
3. **岗位码放开可改**：两域口径统一（格式 + 唯一校验、自身同值豁免）。
4. **出口带 `code`**：管理面（明细 / 树节点）与只读出口（`OrgDept`）均返回；bms 组织选择字段族可见。

**不在本期**：部门编码不参与数据范围 / 权限判定（`@dept_subtree` 仍按 `dept_id` 与 `ancestors` 展开）；编码不进「名称回显」契约（`OrgNameRef` 只回名称与状态）；不新增按编码检索端点（编码随列表 / 树返回，前端本地过滤即可）。

## 2. 口径与决策 <a id="decision"></a>

| # | 待定项 | 结论 |
| --- | --- | --- |
| 1 | 必填与唯一范围 | **必填 + 租户内唯一**（`(code, deleted_at)` 复合唯一，软删除后可复用） |
| 2 | 可改性 | **创建后可修改**（含内置 / 存量行；内部引用一律 `dept_id`，无副作用） |
| 3 | 格式与产生方式 | **手工填写 + 格式约束**（默认 `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`，1~64 位字母 / 数字 / 下划线 / 连字符） |
| 4 | 存量回填 | **`DEPT` + 定长 4 位序号**（按 `id` 升序，超 9999 自动扩位） |
| 5 | 岗位码 | **同步放开可改**（口径与部门编码一致） |
| 6 | bms 侧 | **同步展示**（部门树节点 label 附编码） |
| 7 | 落点 | **父任务 `01_02` 重开 + 本嵌套子任务**；子任务交付后父任务收口 |

**格式参数的默认值差异（说明）**：岗位码默认正则沿用历史值 `^[A-Za-z][A-Za-z0-9_]{0,31}$`（无连字符、上限 32 位），部门编码默认正则取本次口径 `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`；两者**各自可经系统参数覆盖**（`org.post_code_pattern` / `org.dept_code_pattern`），参数缺失或非法一律**回落默认值**（不因配置错误拒绝写入）。

## 3. 数据模型与迁移 <a id="data"></a>

### 3.1 表结构变更

| 表 | 变更 | 约束 / 索引 |
| --- | --- | --- |
| `org_dept` | 新增 `code` VARCHAR(64) NOT NULL | `uq_org_dept_code_deleted_at`（`code` + `deleted_at` 复合唯一）；列级 `code` 无 `server_default`（新建必填） |
| `org_post` | **无结构变更**（仅放开 `code` 可改的应用层行为） | 既有 `uq_org_post_code_deleted_at` 不变 |

字段口径与变更记录回写[表文件 org_dept.md](../../../../../../../设计/数据库设计/数据表设计/org_dept.md)。

### 3.2 迁移 `0003_dept_code`（`org:tenant` 链）

| 步骤 | 动作 | 说明 |
| --- | --- | --- |
| 1 | `batch_alter_table` 加列 | `code`（`nullable=True`）——先可空，容纳存量行 |
| 2 | 回填 | 按 `id` 升序取存量行，逐行写 `DEPT` + `f"{序号:04d}"`（序号自 1 起，`> 9999` 自然扩位）；**回填后各租户库内编码唯一**（序号由 `id` 唯一派生） |
| 3 | 置非空 + 唯一约束 | `batch_alter_table` 内 `alter_column(nullable=False)` + `create_unique_constraint(uq_org_dept_code_deleted_at)` |
| 4 | `downgrade` | `drop_constraint`（唯一）→ `drop_column`（`code`）；「部门编码可改」为应用层行为，无数据回滚项 |

- 全程经 `batch_alter_table`（SQLite 重建表 + 四库通用写法），不含方言专用类型；
- 回填**只读索引与 `id`**，不触碰 `parent_id` / `ancestors` / `name`，移动与子树语义不受影响。

**校验次序（`create_dept`）**：① 编码格式 → ② 编码唯一 → ③ 父部门存在且启用 → ④ 同父名称唯一 → ⑤ 子节点数上限 → ⑥ 深度上限 → ⑦ 落库 + 事件。**与既有次序的差异**：编码校验前置（与 `create_post` 的「格式 → 归属 → 唯一」略有不同——部门侧的编码唯一早于父级校验，便于一次性给出最具体的错误）。

## 5. 岗位码放开可改 <a id="post-code"></a>

| 项 | 变更前 | 变更后 |
| --- | --- | --- |
| `PostUpdateRequest` | 无 `code` | 增 `code`（可空＝不改；提供且与现值不同才走校验与赋值） |
| `PostService.update_post` | `code` 不可改 | `code` 可改：**格式校验 → 唯一校验（自身豁免）→ 赋值** |
| 错误码 | 复用 `330032` / `330036` | 不变（同一码族，语义一致） |
| 契约面 | `PostItem.code` 已在响应 | 不变（请求面新增可选字段，**加性变更**） |
| 文档 | 模型 / 表文件 / 概设标注「创建后不可改」 | 全部改为「可改」，并在表文件变更记录登记 |

## 6. 契约与门禁 <a id="contract"></a>

| 面 | 变更 | 门禁结论 |
| --- | --- | --- |
| 管理面（`/org/depts`） | `DeptItem` / `DeptTreeNode` 增 `code`；`DeptCreateRequest` 增必填 `code`；`DeptUpdateRequest` 增可选 `code` | **请求面新增必填字段属破坏性变更**：新建部门接口的既有调用方必须补 `code`（前端同步改；bms 不调用管理面） |
| 管理面（`/org/posts`） | `PostUpdateRequest` 增可选 `code` | 加性，兼容 |
| 出口（`/org/data-source/dept-tree`） | `OrgDept` 增 `code` | **加性**（`contract_gate` 「只加不删」放行，无需更新基线 / 不升版本） |
| 契约快照 | `deploy/contracts/org.json` 重生成 | `ops.contract_snapshot check` 零漂移 |
| 前端类型 | `@mdm/api-types` 重生成 | `pnpm run api-types:gen:check` 零漂移 |

**关于「新建部门必填 `code`」的破坏性判定**：`contract_gate` 的结构化判定只拦「删除路径 / 操作 / 响应码 / schema / schema 属性」，**新增字段一律放行** → 门禁通过；但该变更对**调用方**是行为性破坏（漏传即 `422`），故：① mdm 前端与原型同批更新；② bms 侧不调用管理面（仅消费只读出口）；③ 在实施记录与需求交付注中显式登记。

## 10. 风险与遗留 <a id="risk"></a>

| # | 风险 / 事项 | 处置 |
| --- | --- | --- |
| 1 | 新建部门请求新增必填 `code` 对**仓外调用方**是行为性破坏 | 仅 mdm 自持管理面（前端同批更新）；已在 §6 显式登记；如需兼容可后续允许后端缺省自动生成（本期不做） |
| 2 | SQLite `batch_alter_table` 重建表时既有命名约束 / 索引的保留 | 迁移用例覆盖「升到 head 零漂移 + 降级往返」；四库演练随部署窗口 |
| 3 | 存量回填编号与外部系统的对账 | `DEPT` + 定长序号仅作初始值，可由管理员改码；改码后如外部已引用需自行同步（编码非内部键） |
| 4 | 岗位码默认正则与部门编码默认正则不一致 | 说明见 §2；两者均可经系统参数覆盖，若需完全统一由运营侧配置 |
| 5 | 协议面「整数 / 字符串」标识口径差异 | 既有遗留（mdm `01_04` 实施记录 §6），本任务不改 |
