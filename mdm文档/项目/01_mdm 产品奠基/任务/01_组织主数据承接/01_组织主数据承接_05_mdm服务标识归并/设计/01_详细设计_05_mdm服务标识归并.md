# 05 详细设计 · mdm 服务标识归并（`org` → `mdm`）

## 1. 目的与口径 <a id="purpose"></a>

mdm 以产品形态接入平台，但内部服务标识沿用承接前的 `org`，形成「产品叫 mdm、服务叫 org、库叫 mdm_org、表前缀 org_、事件域 org.*、对外域段 org」六处口径分裂；后续每新增一个主数据域（参考数据域等）都得再起一个与产品名无关的服务名。另有平台侧耦合：bms 在 `SERVICE_CATALOG` / `PRODUCT_ROUTES` / `DATA_SOURCE_CATALOG` 三个常量里写死 mdm 的服务行、产品路由与数据源条目。

本任务按 2026-10-23 拍板做两件事：**① 服务标识统一为 `mdm`**（包 / 目录保留分类）；**② 产品登记改为产品仓自持清单 + 装载时注册**，bms 不持有产品字面量。

**唯一事实源**：表结构只在各表文件（`mdm文档/设计/数据库设计/数据表设计/*.md`）维护；本文档只写**变更增量**与跨仓机制。通用约定与方言见 bms《数据库设计 · 数据规范》。

## 5. 产品登记清单与装载时注册 <a id="registry"></a>

### 5.1 清单结构 <a id="manifest"></a>

mdm 仓 `deploy/registry/mdm.json`（三类记录，字段与基座记录一一对应）：

```json
{
  "product_key": "mdm",
  "services": [
    {
      "module_key": "mdm", "service_key": "mdm", "name": "mdm 主数据服务",
      "table_prefix": "mdm_", "event_domain": "mdm", "errcode_segment": "33",
      "service_group": "product", "build_batch": 3,
      "service_version": "0.1.0", "contract_version": "0.1.0",
      "product_key": "mdm", "status": "enabled"
    }
  ],
  "product_routes": [
    { "product_key": "mdm", "domain": "mdm", "service_key": "mdm", "description": "mdm 主数据域（对外 /api/mdm/v1/mdm/...）" }
  ],
  "data_sources": [
    {
      "data_source_key": "mdm_dept", "name": "部门", "kind": "dict",
      "data_source": "mdm.mdm.dept", "origin": "product", "product_key": "mdm",
      "path": "/data-source/dept-tree", "allowlist": ["code", "label"], "cascade": true,
      "strategies": ["select", "region", "match"], "status": "enabled"
    },
    {
      "data_source_key": "mdm_post", "name": "岗位", "kind": "dict",
      "data_source": "mdm.mdm.post", "origin": "product", "product_key": "mdm",
      "path": "/data-source/posts", "allowlist": ["code", "label"], "cascade": false,
      "strategies": ["select", "match"], "status": "enabled"
    }
  ]
}
```

### 5.2 单一来源与零漂移 <a id="manifest-source"></a>

- **单一来源**仍为 mdm 代码清单（`services/module_registry.py` / `table_registry.py` / `form_registry.py` 与数据源清单）；`deploy/registry/mdm.json` 由 `ops/export_registry.py` **生成**。
- `ops/check_registry.py` 断言「JSON ↔ 代码清单」逐字段同值（零漂移），并入预检与 CI；手改 JSON 即红。
- mdm `services/module_registry.py::validate_local_catalog()` 的「两侧同值」基准由 **bms 平台常量**改为**本仓清单 JSON**（同仓两处同值仍能防漂移，且不再依赖 bms 常量）。

### 5.3 bms 侧装载 <a id="manifest-load"></a>

- 新增 `bms_core/registry/products.py`：`ProductRegistryManifest`（三类记录）+ `load_product_manifests(paths)` + `validate_manifest()`（字段合法与唯一、`product_key` 与产品档案一致）。
- **配置**：`[registry].product_manifests: list[str]`（缺省 `[]`）；`config.dev.toml` 指向 `../mdm/deploy/registry/mdm.json`。环境变量 `BMS_REGISTRY__PRODUCT_MANIFESTS` 可覆盖（部署态注入）。
- **运行时（平台服务）**：装配期装载清单 → 与 `SERVICE_CATALOG` / `PRODUCT_ROUTES` / `DATA_SOURCE_CATALOG` 合并为应用级视图（同键同值去重、异值即拒），供 `/api/v1/data-sources`、服务目录校验与网关派生使用。
- **运行时（产品服务 mdm）**：不读文件，直接经应用工厂钩子注入本产品记录（`service_records()` / 新增 `product_route_records()` / 新增 `data_source_records()`），与平台清单合并同值。
- **离线（网关生成）**：`ops/gateway_config.py` 按配置路径装载清单 → `render_apisix_config(services=..., routes=...)` 合并生成；**清单缺失即降级为空**（仅平台路由），并在输出中标注「产品清单未装载」，不阻断 CI。
- **失败分支**：清单 JSON 非法 / 与产品档案不符 → 平台服务拒启与 `gateway_config check` 失败（`CatalogError`）；清单路径不存在 → 告警 + 空合并（CI 与未挂载产品的环境可跑）。

### 5.4 产品路由与数据源注入通道 <a id="hooks"></a>

| 钩子 | 落点 | 语义 |
| --- | --- | --- |
| `service_records()` | 已有 | 本服务补充的服务目录记录 |
| `product_route_records()` | 新增（`application.py` + `module_registry.py`） | 本产品的产品级路由映射；基座与 `PRODUCT_ROUTES` 合并并同键同值去重 |
| `data_source_records()` | 新增（`application.py` + `datasource/registry.py`） | 本产品的数据源登记条目；基座与 `DATA_SOURCE_CATALOG` 合并 |
| `table_records()` / `form_records()` | 已有 | 表归属 / 表单标识，口径不变 |

## 6. 库名派生去重 <a id="dbname"></a>

- `db/keys.py`：`platform_database_name(service, prefix)` 与 `tenant_database_name(service, basis, prefix)` 在 `prefix == service` 时返回 `service` / `{service}_{basis}`（不重复拼接）；`prefix != service` 行为完全不变（平台 `bms` 与各服务不受影响）。
- 效果：mdm `[database].name_prefix = "mdm"` + 服务 `mdm` → 平台库 `mdm`、租户库 `mdm_{租户}`、归档库 `mdm_archive`（`archive_database_name` 不涉服务，保持 `{prefix}_archive`）。
- 校验：新增用例覆盖 `prefix == service` 与 `prefix != service` 两侧；`_checked_database_name` 规则不变。

## 7. 迁移改写 <a id="migration"></a>

- 目录 `alembic/versions/org/{tenant,platform,archive}` → `alembic/versions/mdm/{...}`；`alembic.ini` 段名与 `version_locations` 同步。
- 脚本 `0001` ~ `0005`：revision id 改 `0001_mdm_tables` …（链内递增不变）；建表 / 索引 / 唯一约束名改 `mdm_*`；`branch_labels` 改 `mdm:tenant`；`down_revision` 链保持。
- 开发 SQLite 库**删库重建**（`database/mdm/` 下旧 `mdm_org_*.db` 一并清理），不写改名迁移。
- `ops/migrate.py` 链名派生随 `local_service_keys()` 自动变 `mdm`，无需硬编码。

## 8. 失败分支与边界 <a id="failure"></a>

| 场景 | 处置 |
| --- | --- |
| 表前缀不属于归属服务 | 基座 `TableOwnershipRegistry._validate_prefix()` 拒启（改名后六表均为 `mdm_`，闭合） |
| 服务行两侧异值 | 合并视图「同键同值去重、异值即拒」，拒启并打印差异 |
| 产品清单缺失（CI / 未挂载环境） | 降级为空清单，网关仅生成平台路由并告警；不静默用旧值 |
| 清单 JSON 非法 | `gateway_config check` 失败、平台服务拒启 |
| 契约 / 事件快照未重生成 | `ops.contract_snapshot check` / `ops.event_contracts check` 失败 |
| 前端仍指向旧域段 | 契约对齐用例失败（前端调用面 ⊆ 契约） |

## 11. 风险与遗留 <a id="risk"></a>

- **跨仓协同面大**：mdm 90+ 文件 + bms 15 文件；bms 侧先合入（清单装载 + 库名去重 + 常量删除），mdm 侧改名随后，二者须同批联调。
- **清单装载依赖路径**：CI 无 mdm 仓时降级为空；部署态须配 `product_manifests`，否则网关缺 mdm 路由（`/readyz` 与日志标注）。
- **镜像名 `mdm-mdm`**：随 `mdm-{service}` 规则产生；如后续觉得冗余，可另立「镜像命名」口径调整，不在本任务。
- **生产未上线**：本次改名不涉及存量数据迁移；一旦上线后再改名须走数据迁移，故须在首次部署前完成。
