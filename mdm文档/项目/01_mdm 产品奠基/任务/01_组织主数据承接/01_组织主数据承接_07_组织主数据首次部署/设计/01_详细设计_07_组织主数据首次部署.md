## 1. 目的与口径 <a id="purpose"></a>

mdm 至今的验证面只有「开发机单测 + CI 静态门禁」，**从未以产品形态落到部署主机**：没有运行镜像、没有服务库、网关无 `mdm` 上游、前端模块未发布。本设计把这条链路一次打通，并让**部署入口只有一处实现**（bms `release.py`），避免产品仓再写一套发布脚本导致回滚与台账口径分叉。

设计约束（2026-11-05 拍板）：

1. 部署入口 = 扩展 bms `scripts/tools/deploy/release.py`，**只加通用参数，不写产品字面量**；
2. 服务器保留 `~/bms` 不动，新增 `~/mdm`（部署主机形态，不迁工作区）；
3. 镜像由 **mdm CI 构建并推送**（SHA 标签），服务器只拉取；
4. 密钥**复用 bms `deploy/.env` 同一套**（服务令牌 / 用户令牌 / 对称密钥）；
5. 库为 MySQL 全量租户：`mdm` / `mdm_demo` / `mdm_acme` / `mdm_archive`；
6. 网关走**注册表模式重渲 + APISIX 文件轮询热加载**，不手改生成物。

## 4. 镜像与 CI <a id="image"></a>

### 4.1 构建上下文与忽略规则 <a id="context"></a>

`bms-core` 是**路径依赖**（`../../bms/backend/libs/bms_core`），镜像内需同时具备 `mdm/` 与 `bms/backend/libs/bms_core`，Docker 只能从单一上下文取其内容 → 上下文上移到**工作区根**（服务器上即仓库父目录）。

忽略规则改由 `mdm/deploy/Dockerfile.dockerignore` 承载（BuildKit 对该文件优先于上下文根的 `.dockerignore`），内容 = 原工作区根 `.dockerignore` 逐条迁入，并补 `bms/deploy/`（部署态变量与生成物不进镜像）。

### 4.2 `image-build` job <a id="ci-image"></a>

```yaml
image-build:
  stage: build
  image: docker:27-cli
  script:
    - . scripts/tools/ci/bms_setup.sh        # 上下文需要 bms 源码（路径依赖）
    - echo "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
    - cd ..
    - docker build --provenance=false -f mdm/deploy/Dockerfile -t "$IMAGE" .
    - docker push "$IMAGE"
```

- `IMAGE = ${MDM_REGISTRY_IMAGE_PREFIX:-$CI_REGISTRY/mjs/mdm}/mdm:$CI_COMMIT_SHORT_SHA`；
- `--provenance=false`：BuildKit 默认 attestation 清单会被 GitLab Registry 拒绝（`blob unknown`，bms 侧实测）；
- 凭据用 **CI 预定义** `CI_REGISTRY_USER` / `CI_REGISTRY_PASSWORD`（mdm 项目无项目级变量，不需要新建）。

### 4.3 覆盖率口径 <a id="ci-coverage"></a>

`backend-test` 改为：

```yaml
variables:
  MDM_COVERAGE_DATA: $CI_PROJECT_DIR/.cache/coverage/.coverage
  MDM_COVERAGE_SOURCE: mdm,services,ops
script:
  - *backend-setup
  - rm -rf "$CI_PROJECT_DIR/.cache/test" "$CI_PROJECT_DIR/.cache/coverage"
  - find "$CI_PROJECT_DIR" -name '*.db' -not -path '*/.git/*' -delete
  - uv run pytest
  - >-
    uv run engkit coverage --root "$CI_PROJECT_DIR"
    --data-file "$MDM_COVERAGE_DATA" --out "$CI_PROJECT_DIR/coverage.json"
    --module mdm --module services --module ops --fail-under 100
coverage: '/percent=(\d+(?:\.\d+)?)/'
```

### 4.4 改名后的重新交付（`944818a` 之后） <a id="rename-redelivery"></a>

`944818a` 把全仓 `org` 统一为 `mdm`（目录 / 包名 / 模块键 / 能力名 / 常量 / 文档），此前部署的镜像与前端产物因此全部过期。重新交付的口径：

| 面 | 旧口径（`dd4eb113`） | 新口径（`944818a` 之后） | 验收方式 |
| --- | --- | --- | --- |
| 服务包 | `services/org/src/mdm/org/` | `services/mdm/src/mdm/mdm/` | 镜像内 `python -c "import mdm"`；`/readyz` |
| 业务域 | `org` | `mdm` | 平台注册表 `sys_domain.domain_key = mdm` |
| 能力名 | `mdm.org.*` | `mdm.mdm.*` | 注册表 `sys_collaboration` / 契约快照 |
| 前端模块键 | `mdm_org` | `mdm` | 产物 `module.meta.json.name = mdm` |
| 宿主入口 | `/mdm_org/0.1.0/remoteEntry.js` | `/mdm/0.1.0/remoteEntry.js` | `modules.json` 与发布台账 |
| 域布局 | `backend/services/org/src/mdm/org/**/*.py` | `backend/services/mdm/src/mdm/mdm/**/*.py` 等五条 | `sys_domain.paths` 重渲后逐字核对 |

**执行顺序**：① 提交改名后的文档 / 测试修复 → ② 手工触发 mdm CI，`docs-links`、`backend-*`、`frontend-*`、`image-build` 全绿 → ③ 服务器 `~/mdm` 快进到同一 SHA → ④ `release.py deploy` 拉新镜像并迁移 → ⑤ `release.py gateway --render` 让注册表路径 / 能力名按新声明重渲 → ⑥ 发布 `mdm` 模块并删除 `mdm_org` 条目。

**为什么必须先重构建**：镜像内的包路径、注册表声明与前端模块键在同一个提交里改名，三者必须来自同一 SHA；混用旧镜像 + 新清单会出现「模块能加载但后端能力名不匹配」的隐性 403，无法作为验收证据。

## 5. 部署入口扩展（bms `release.py`） <a id="entry"></a>

### 5.1 新增通用参数 <a id="entry-params"></a>

| 参数 | 缺省 | 含义 |
| --- | --- | --- |
| `--repo-root` | 脚本所在仓根 | `ops` 脚本定位与只读挂载基准（产品仓部署时指向 `~/mdm`） |
| `--compose-file` | `compose/bms.yml` | compose 文件（相对 `deploy-dir`） |
| `--service` | 平台服务清单 | 目标服务键（改为自由字符串；`--all` 取 `compose config --services`） |
| `--container-name` | `bms-{service}` | 容器名模板（mdm 为 `mdm`） |
| `--tag-env` | `BMS_TAG_{SERVICE}` | 镜像标签变量名模板（mdm 为 `MDM_TAG`） |
| `--image-prefix-env` | `REGISTRY_IMAGE_PREFIX` | 镜像前缀变量名（mdm 为 `MDM_REGISTRY_IMAGE_PREFIX`） |
| `--health-path` | `/readyz` | 容器内就绪探测路径 |
| `--gateway-path` | `/api/{service}/v1/__gate__` | 网关冒烟路径模板（mdm 用产品命名空间 `/api/mdm/v1/mdm/__gate__`） |
| `--skip-gateway-probe` | 关 | 容器门禁跳过「网关可达」第三步（首部署路由尚未生成时用；跳过记入发布日志） |
| `--init-command` | `python -m ops.init_schema --service {service}` | 建表 / 迁移命令模板；含 `{tenant}` 时逐租户执行，含 `{tenants}` 时展开为 `--code X --code Y` |
| `--provision-command` | 空 | 建库命令模板（同上占位符）；缺省不建库 |
| `--db-grant-pattern` | `bms\_%` | 应用账号授权库模式（仅 `bootstrap` 使用） |

### 5.2 新子命令 <a id="entry-cmds"></a>

| 子命令 | 作用 |
| --- | --- |
| `provision` | 按 `--provision-command` 在目标镜像内建库（幂等），供首次部署 |
| `gateway [--render]` | 无 `--render`：注册表对账（重渲结果 ↔ 仓库生成件逐字比）；`--render`：**按注册表重渲并写回** `deploy/gateway/apisix.yaml`（APISIX 文件轮询自动热加载） |
| `exec -- <命令>` | 通用一次性执行（种子 / 排障），不引入产品字面量 |

### 5.3 mdm 调用形态 <a id="entry-mdm"></a>

```bash
cd ~/mdm
python3 ~/bms/scripts/tools/deploy/release.py \
  --repo-root ~/mdm --deploy-dir ~/mdm/deploy \
  --compose-file compose/mdm.yml \
  --container-name mdm --tag-env MDM_TAG --image-prefix-env MDM_REGISTRY_IMAGE_PREFIX \
  --health-path /readyz --gateway-path /api/mdm/v1/mdm/__gate__ \
  --init-command "python -m ops.migrate {tenants}" \
  --provision-command "python -m ops.provision {tenants}" \
  <子命令>
```

## 6. 服务器部署步骤 <a id="server"></a>

```text
① 克隆 ~/mdm（与 ~/bms 平级）→ 写 deploy/.env（库连接、平台网络、密钥取 bms 同值）
② release.py provision                              # 建 mdm / mdm_demo / mdm_acme / mdm_archive
③ release.py deploy --service mdm --tag <sha> --skip-gateway-check --skip-gateway-probe
                                                    # 迁移 → 起容器 → 门禁（容器 healthy + /readyz）
④ bms release.py gateway --render                   # 平台侧按注册表重渲 + APISIX 热加载
⑤ release.py health-gate --service mdm              # 网关门禁复核（此时产品路由已生成）
⑥ 断言 /api/mdm/v1/mdm/... 无凭据 401，带令牌 200
⑦ bms ops.seed_platform --tenant demo / acme（平台 + 产品同构声明，一个 XA 事务）
⑧ node:24 容器内 bms release-module.mjs publish --module mdm
```

**顺序口径**：③ 的两个跳过各管一件事——`--skip-gateway-check` 跳过 **bms 平台注册表对账**（mdm 仓没有 `deploy/gateway/` 生成件，对账对象不适用）；`--skip-gateway-probe` 跳过容器门禁里的**网关可达**探测（首部署时 `mdm` 声明尚未生成路由，探测必然失败）。两者都写入发布日志留痕。因此 ③ 之后必须先做 ④，再用 ⑤ 单独复核——复核通过即视为门禁通过。④ 的重渲是幂等的：注册表未变化时生成件逐字不变。

### 6.1 库与账号 <a id="db"></a>

| 库 | 键 | 生成方式 |
| --- | --- | --- |
| `mdm` | `platform_mdm` | `[database].name_prefix = mdm` + 「前缀 = 服务标识去重」 |
| `mdm_demo` / `mdm_acme` | `tenant_mdm_{code}` | 同上 + 租户编码（与 `BMS_DEPLOY_TENANTS` 同集） |
| `mdm_archive` | `platform_archive` | `archive_database_name(prefix="mdm")` |

应用账号 `mdm_app`：`GRANT ALL ON \`mdm\\_%\`.*`（与 bms `bms_app` 同形）。

### 6.2 `.env` 键位（相对 bms 的差异） <a id="env"></a>

| 键 | 值 |
| --- | --- |
| `PLATFORM_NETWORK` | `deploy_default`（bms 部署创建） |
| `MDM_REGISTRY_IMAGE_PREFIX` | `192.168.0.107:5050/mjs/mdm` |
| `MDM_TAG` | 本次 SHA |
| `BMS_DATABASE__PLATFORM__URL_TEMPLATE` | `mysql+aiomysql://mdm_app@mysql:3306/{database}` |
| `BMS_DATABASE__TENANTS__URL_TEMPLATE` | 同上模板 |
| `BMS_DATABASE__*__PASSWORD` | 与 `BMS_APP_DB_PASSWORD` 同值 |

| `BMS_EDGE__PROVIDER` | `service_jwt`（必须；网关转发服务 JWT + 用户身份头，`null` 会把用户请求当未授权服务身份） |

### 6.3 验收令牌与最小样例数据 <a id="accept-data"></a>

**令牌**：不把口令写进仓库或公开文档。按 bms 同款种子命令重置 demo 租户管理员，口令只落 `bms文档/用户文档/本地资源.md`（gitignored）：

```bash
cd ~/bms
docker compose run --rm --no-deps platform \
  python -m ops.seed_user --tenant demo --username admin --reset-password
```

重置后用 `POST /api/identity/v1/auth/login` 取 `access_token`，后续五个出口统一带 `Authorization: Bearer <token>`。

**样例数据（demo 租户，最小覆盖集）**：

| 对象 | 编码 | 名称 | 关系 |
| --- | --- | --- | --- |
| 部门 1 | `MDM-ROOT` | 总部 | 根部门 |
| 部门 2 | `MDM-TECH` | 技术部 | `parent_id` = 部门 1 |
| 岗位 1 | `MDM-PM` | 项目经理 | 归属技术部 |
| 岗位 2 | `MDM-DEV` | 开发工程师 | 归属技术部 |

分配：`PUT /mdm/user-posts/{admin_id}` 写入两个岗位（其中一个设为主要岗位），`PUT /mdm/user-depts/{admin_id}` 写入技术部。这样 `dept-tree` 有嵌套、`posts?include_children` 有子树差异、`users` 有部门过滤命中、`resolve-names` 有可回显 ID、`user-roles` 有岗位链与部门链并集。

> 样例数据只建在 `mdm_demo`，验收结束不删除（演示租户保留可复现数据）；删库 / 清表仅用于真库迁移的临时对象。

## 7. 真库迁移（PostgreSQL / 达梦 DM8） <a id="real-db"></a>

### 7.1 目标与对象拓扑 <a id="real-db-target"></a>

MySQL 四库已在首次部署时迁移到 head；本节补 **PostgreSQL 16** 与 **达梦 DM8** 的 `mdm:tenant` 链真库演练，证明迁移脚本不依赖 SQLite / MySQL 方言：

| 方言 | 对象 | 连接串 / 模式 | 建对象 | 清理 |
| --- | --- | --- | --- | --- |
| PostgreSQL | 独立库 `mdm_migrcheck_pg` | `postgresql+psycopg://postgres@192.168.0.107:5432/mdm_migrcheck_pg` | `CREATE DATABASE`（管理库 `postgres`） | `DROP DATABASE` |
| 达梦 DM8 | 独立模式 `MDM_MIGRCHECK` | `dm+dmPython://SYSDBA@192.168.0.107:5236` + `--schema MDM_MIGRCHECK` | `CREATE SCHEMA`（SYSDBA） | `DROP SCHEMA ... CASCADE` |

对象名带固定前缀 `mdm_migrcheck` / `MDM_MIGRCHECK`，与 bms 三库测试对象（`bms_test_*` / `BMS_TEST_*`）区分，避免误删生产库。

**真库演练检出的两处缺陷（2026-11-05）**：

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 达梦迁移报 `UnsupportedCompilationError: ColumnComment` | Alembic 未给 `dm` 方言注册列注释渲染器 | `alembic/env.py` 补 `@compiles(ColumnComment, "dm")`，按达梦 Oracle 兼容语法输出 `COMMENT ON COLUMN … IS …` |
| 2 | 库结构比对发现 `sys_outbox` 缺 `trace_id` | 基座模型已增链路 id，mdm `0002_outbox_tables` 建表时未同步；域清单不比对基础设施表，历史用例未覆盖 | 新增增量迁移 `0006_outbox_trace_id`（可空列，既有库随部署直接升级），并把「发件箱含 `trace_id`」纳入迁移用例断言 |

> 达梦的标识符按大写折叠，且 dmSQLAlchemy 的 `compare_metadata` 反射路径存在 `get_multi_table_comment` / `dm_tablespace` 缺陷；故达梦零漂移采用**结构快照比对**（表 / 列 / 可空 / 类型 / 索引 / 主键，类型按达梦同义词归一），PostgreSQL 仍用 Alembic `compare_metadata`。两者都要求差异为空。

### 7.2 执行链路 <a id="real-db-flow"></a>

```bash
cd ~/mdm/backend
# ① 建对象（管理连接；达梦用 SYSDBA）
psql "postgresql://postgres:***@192.168.0.107:5432/postgres" -c 'CREATE DATABASE mdm_migrcheck_pg'
disql SYSDBA/***@192.168.0.107:5236 -e 'CREATE SCHEMA MDM_MIGRCHECK'

# ② 迁移（单库模式；达梦经 --schema 指定模式）
python -m ops.migrate --target tenant \
  --url "postgresql+psycopg://postgres:***@192.168.0.107:5432/mdm_migrcheck_pg"
python -m ops.migrate --target tenant \
  --url "dm+dmPython://SYSDBA:***@192.168.0.107:5236" --schema MDM_MIGRCHECK

# ③ 幂等复跑（应「已是最新（跳过）」）
# ④ 零漂移（Alembic compare_metadata 对 mdm:tenant 清单元数据）
# ⑤ 清理（DROP DATABASE / DROP SCHEMA ... CASCADE）
```

**零漂移判据**：迁移后库内 `mdm_dept` / `mdm_post` / `mdm_user_post` / `mdm_user_dept` / `mdm_role_post` / `mdm_role_dept` 六表 + `sys_outbox` / `sys_event_consumed` / `sys_event_dead_letter` 三基础设施表齐备；`compare_metadata` 对 `mdm:tenant` 清单元数据的差异为空（基础设施表与版本表按既有口径排除）。

### 7.3 自动化落点 <a id="real-db-test"></a>

新增 `backend/tests/integration/test_mdm_tenant_migration_real.py`，标记 `integration`：

- **环境守卫**：`MDM_TEST_PG_URL` / `MDM_TEST_DM_URL` 未配置即 `skip`，不阻塞默认用例；
- **参数化**：`postgres` / `dm8` 两参数，达梦额外读 `MDM_TEST_DM_SCHEMA`（缺省 `MDM_MIGRCHECK`）；
- **对象生命周期**：库 / 模式由执行脚本创建，用例只建删该模式内的表（`mdm_migrcheck` / `MDM_MIGRCHECK` 前缀对象），不触碰 `mdm_demo` / `mdm`；
- **断言**：head 修订一致、九表齐备（含 `sys_outbox.trace_id`）、PG `compare_metadata` 空差异、达梦结构快照差异为空、二次迁移幂等跳过。

> 该用例默认跳过，CI 不采集其覆盖；生产代码无新增分支，覆盖率门禁不受影响。

## 8. 前端模块发布 <a id="frontend"></a>

1. mdm CI `frontend-build` 增加 `artifacts.paths: [frontend/modules/mdm/dist/]`（保留 30 天）；
2. 服务器按 `GET /projects/15/jobs/artifacts/<sha>/download?job=frontend-build` 取包，解出 `frontend/modules/mdm/dist/`；
3. 用 `node:24` 容器（挂载 `~/bms` 与解包目录）执行：
   ```bash
   docker run --rm -v ~/bms:/bms -v <产物根>:/artifact -w /bms/frontend node:24 \
     node scripts/release-module.mjs publish --module mdm --module-dir /artifact/modules/mdm
   ```
4. 产物落 `~/bms/frontend/releases/mdm/<版本>/`，`release-log.json` / `release-log.md` 记台账；宿主清单 `modules.json` 同步。
5. **删除旧条目**：发布 `mdm` 成功后，从 `~/bms/frontend/apps/desktop/public/modules.json` 删除 `mdm_org` 条目（决策 14），再跑 `node scripts/check-module-manifest.mjs` 确认清单只剩可加载模块、版本发现一致。

> 四关强校验（`dist/remoteEntry.js` / `module.meta.json` / sourcemap / 体积预算）由发布脚本自身执行，服务器只提供产物与目标仓。改名后的产物元数据应为 `{"name":"mdm","version":"0.1.0","contractVersion":2}`，入口路径 `mdm/0.1.0/remoteEntry.js`。

## 11. 风险与回退 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 镜像构建时 `uv sync --frozen` 因 bms `main` 头变动失败 | `BMS_REF` 钉 SHA（CI 变量），构建可复现 |
| 改名后 CI 在 `docs-links` / 契约快照处失败 | 本次已修 5 处跨仓断链；契约快照在改名提交内已同步，若 CI 仍报漂移按输出重导并复核 |
| 迁移在真实库报方言差异（SQLite 通过、MySQL 失败） | 首次部署即验；失败保留容器日志，库为空的库可 `--skip-...` 重建 |
| PG / 达梦对象残留 | 对象名固定带 `mdm_migrcheck` / `MDM_MIGRCHECK` 前缀，清理脚本只匹配该前缀；清理前先确认无业务连接 |
| 达梦 `SYSDBA` 连接串中的密码进入日志 | `ops.migrate` 只打印脱敏连接串；执行记录不贴明文，凭据取本地资源 |
| APISIX 未热加载 | 检查 `apisix.yaml` 挂载与 `config.yaml` 的 `standalone` 轮询；必要时 `docker restart bms-apisix` |
| 前端产物版本与宿主清单不匹配 | `release-module.mjs` 四关拒收；回滚用 `releases/` 上一版本目录重发 |
| 删除 `mdm_org` 后旧页面 404 | 新模块键 `mdm` 已发布且清单校验通过才删；回滚以发布台账恢复旧条目 |
| 密钥不一致导致 401 连环 | 两仓 `.env` 同值核对（`BMS_SERVICE_TOKEN__KEYS` 的 kid 与 key 必须成对） |
